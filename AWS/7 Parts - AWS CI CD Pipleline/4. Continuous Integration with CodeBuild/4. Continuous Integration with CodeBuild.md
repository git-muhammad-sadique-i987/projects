## Setting up a CodeBuild Project

AWS CodeBuild is a fully managed continuous integration service that automates the software build process. Think of it as a robot that takes your code, prepares it, tests it, and packages it up, ready for deployment, without you having to do it manually each time.

Engineers love continuous integration tools like CodeBuild because you don't have to manually set up and manage any build servers yourself, and you only pay for the compute time you use for building your projects (instead of entire servers that are idle most of the time).

My CodeBuild project's source configuration means that, CodeBuild doesn't know where your web app's code lives! Source means the location of the code that CodeBuild will fetch, compile, and package into a file you can deploy.

We're choosing GitHub as our source provider because that's where we've stored our web app's code. By connecting CodeBuild directly to GitHub, we're creating a seamless pipeline where code changes automatically flow into our build process.

## Connecting CodeBuild with GitHub

When connecting to GitHub, CodeConnections gives you a few different options, each with their own trade-offs:

GitHub App: This is generally the simplest and most secure option. AWS manages the application and connection, reducing the need for you to handle tokens or keys directly. It's recommended for most use cases due to its ease of use and enhanced security.

AWS CodeConnections is like a secure bridge between AWS and your external code repositories. Instead of dealing with the headache of managing API keys, tokens (like GitHub's Personal Access Tokens!), or SSH credentials, CodeConnections handles all that authentication complexity for you - so you can focus on building your application.

## CodeBuild Configurations

### Environment

The environment in AWS CodeBuild refers to the configuration settings that determine how and where your code is built. It's like setting up a virtual workspace with all the necessary tools and resources for your build process to run smoothly.

A CodeBuild environment encompasses several key aspects:

Operating System: Specifies the OS for the build environment (e.g., Amazon Linux, Ubuntu, Windows Server).

Runtime: Determines the programming language and its version (e.g., Java, Python, Node.js).

Compute Resources: Defines the computing power allocated to the build, influencing build speed and cost.

Buildspec File: A YAML file that outlines the build commands and settings.

### Artifacts

Build artifacts are the tangible outputs of our build process. They're what we'll actually deploy to our servers or distribute to users.

Our compiled applications, libraries, or any output files from your build need a safe, accessible home after the build finishes. 

S3 is perfect for this - it's a highly reliable and scalable storage solution that's also in our AWS environment (which makes the artifact easily accessible for deployment later).

### Packaging

When setting up CodeBuild, I also chose to package artifacts in a zip file because of smaller size, better management of one tidy package as oppose to multiple files. Zip file keeps the simplicity. 

### Monitoring

For monitoring, I enabled CloudWatch Logs, which is a monitoring service that collects and tracks logs from AWS services. In this project, CloudWatch will record everything that happens during the build process, including the commands that are run, the output of those commands, and any errors that occur. This is incredibly useful for debugging and understanding what went wrong if a build fails.

## buildspec.yml

My first build failed because there was no buidspec.yml file in my GitHub repository. The file is needed because it is like a step-by-step instruction manual. It goes through each phase in order - install, pre_build, build, then post_build - running the commands you've specified in each section.

The phases in my buildspec.yml file are:
1. Install - The "prep work" phase - here, we're telling CodeBuild to use Java 8.
2. pre_build -  Tasks to do before the main building starts. Here, we're grabbing a security token so we can access our dependencies. 
3. Build - Where the actual building happens. We're using Maven (a popular Java build tool) to compile our code.
4. Post_build - The finishing touches after the main build is done. Here, we're packaging everything into a WAR file (a format for web applications).

## Success!

My second build also failed, but with a different error that said "COMMAND_EXECUTION_ERROR: Error while executing command: mvn -s settings.xml compile. Reason: exit status 1"

CodeBuild still can't access the settings.xml file.

This usually happens because our CodeBuild service role doesn't have permission to access CodeArtifact, which is needed to download project dependencies.

To fix this, we need to grant CodeBuild's IAM role the permission to access CodeArtifact.

To resolve the second error, I attached "codeartifact-nextwork-consumer-policy" to role "codebuild-nextwork-devops-cicd-service-role"

After this step the CodeBuild had then sufficient permissions on setting.xml file.

The Build succeeded this time. 

To verify the build, I checked the S3 bucket that i created for this project and there it was.... The artifact that was created after successful build.
